## はじめに​  

私は昨日、小さなシェルスクリプトを作った。​  

Claude Codeの対話セッションをtmuxで保持し、SSHでLAN内の別のマシンから接続できるようにする。ただそれだけの仕組みである。​  

本人が休暇中でも、その人の作業セッションへ接続して、AIに質問できる。​  

この仕組みに、私は「Ghost」と名づけた。​  

最初は、ちょっと便利な遠隔操作ツールのつもりだった。​  

ところが、実際に作って動かしてみると、見えてくるものが次々に変わっていった。​  

担当者本人を呼び出さなくても、その人のエージェントがリポジトリ、Git履歴、設計文書、会話記録、テスト結果を調査して答えられるのではないか。​  

プロジェクト管理者のエージェントが、各メンバーのGhostを訪ねて進捗と問題点を取材すれば、人間が報告書を書いたり、進捗会議へ集まったりする必要も減るのではないか。​  

さらに、組織内のGhost同士を接続できる。インターネット上で公開されたGhost同士も接続できる。本、ソフトウェア、制度、組織そのものが、それぞれ自分について調査して答えるGhostを持つこともできる。​  

気がつけば話は、単なる端末共有から、組織の同期通信を根本的に減らす構想へ発展していた。​  

中心にある原則は、驚くほど単純である。​  

> **本人に聞くな、エージェントに聞け。**

エージェントは、本人になりすまして答えるのではない。​  

本人の代わりに、その人の仕事を調査する。​  

そして、調べても決められなかった問題だけを、本人へ渡す。​  

本稿に収録したのは、この構想が一晩の対話から次々に姿を現していった記録である。​  

話題は、Ghostの公開デモ、Ghostについて答える "Ghost Ghost"、GhostNet Global、ブラウザSSH、所有者と外部質問者の分離、話者を取り違える生成AI、決定論的な発話parser、さらには複数のGhostによるシステムの競作へと、際限なく広がっていく。​

## Ghost Session Contract​  

`ghost publish` が、セッションと一緒に次の情報を宣言します。​  

```yaml​  
protocol_version: 1​  
session: work​  
command:​  
  name: claude​  
  argv:​  
    - claude​  
input:​  
  enter: submit​  
  modified_enter: newline​  
terminal:​  
  extended_keys: required​  
lifecycle:​  
  client_disconnect: detach​  
  session_exit: owner_only​  
```

これをmDNSのTXTレコードに全部詰め込む必要はありません。mDNSには発見に必要な短い情報だけ載せ、詳細はServer側の管理ファイルから取得する形がよいでしょう。​  

## 1. 送信キー問題​  

利用者の `~/.tmux.conf` に依存すること自体をやめます。​  

Ghost専用のtmuxサーバーと設定を持たせます。​  

```bash​  
tmux -L ghost -f ~/.config/ghost/tmux.conf ...​  
```

Ghostが管理する設定には、最初から必要条件を書く。​  

```tmux​  
set -s extended-keys on​  
set -as terminal-features 'xterm*:extkeys'​  
```

これなら、​  

- ユーザーの既存tmux環境を壊さない​  
- ホストごとの設定差を排除できる​  
- Ghostの入力仕様をGhost自身が保証できる​  

となります。​  

さらに `ghost doctor` を用意して、端末・tmux・SSHの能力を事前検査できると美しい。​  

```console​  
$ ghost doctor​  
[OK] tmux supports extended keys​  
[OK] terminal reports xterm-256color​  
[OK] Ghost tmux configuration​  
[OK] SSH key​  
```

`publish` と `join` の内部でも同じ検査部品を使います。ここは山田式UNIX部品化がそのまま効きます（笑）。​  

## 2. 終了キー問題​  

これは「ClaudeはCtrl+D二回、Codexは一回」という対応表を作る方向へ行かないほうがよいです。対応表は無限に増えます。​  

Ghost Clientがしたいことを二つに分離します。​  

- Ghostから離脱する​  
- Ghost内のプロセスを終了する​  

`ghost join` からの通常の退出は、常に「detach」とします。中で動いているClaudeやCodexには終了キーを送りません。​  

たとえばSSHのエスケープに似たGhost専用操作を設けます。​  

```text​  
Ctrl+] d   Ghostからdetach​  
Ctrl+] ?   Ghost操作一覧​  
Ctrl+] i   セッション情報​  
```

セッション内プロセスの終了は、原則としてServer側の所有者だけが行う。必要なら明示的な管理コマンドにします。​  

```console​  
ghost stop work​  
```

これによってClientは、ClaudeやCodexの終了方法を知る必要がなくなります。​

> **組織内の質問を、人から知識空間へルーティングし直す。**

現在：​  


これは「会議効率化ツール」ではありません。組織の通信アーキテクチャの変更です。​
